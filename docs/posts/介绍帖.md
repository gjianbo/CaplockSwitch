# 【自荐】CapsSwitch —— 把 Caps Lock 变成输入法切换键（Windows 托盘小工具）

> 一句话：**单独按 Caps 切输入法，Shift+Caps 保留原生大写，Ctrl+Caps 随时开关。**
> 单文件、绿色免安装、零运行时依赖、纯 Win32 手写。

---

## 一、为什么要做这个

从 Mac 过来的人大多有个改不掉的手癖：**按 Caps Lock 切中英文**。

而 Windows 上 Caps Lock 的位置极好、使用率极低 —— 它天生就该被拿来做这件事
（macOS 上「Caps Lock → 切换输入法」甚至是系统设置里的一个官方选项）。

现成的方案不是没有：AutoHotkey 要额外装运行时、要维护脚本；输入法自己的自定义
热键又只管得了那一家输入法。于是就动手写了一个：**小而专，只做这一件事，做完就退到托盘里不再打扰你。**

---

## 二、它做什么

| 你的操作 | 它的反应 |
|---|---|
| **单独按 Caps Lock** | 发送你配置的输入法切换快捷键（默认 `Ctrl + Space`） |
| **Shift + Caps Lock** | 完整放行给系统，**原生大写锁定**照旧（左右 Shift 都行） |
| **Ctrl + Caps Lock** | 切换「启用 / 暂停」，**两种状态下都有效** |
| **Alt / Win + Caps Lock** | 只吞掉 Caps，不做任何动作 |
| 暂停状态下按 Caps | 完全不干预，Caps Lock 恢复系统原生行为 |

如果某个程序**自己就要接管 Caps**（典型：悠悠远程、ToDesk 这类远程控制软件），
可以在设置里把它加入**忽略列表**（也可以直接写 `config.ini` 的 `[Ignore]` 段，最多 16 条）。
该程序位于前台时，CapsSwitch 完全不拦截任何 Caps 按键 —— 包括 `Ctrl+Caps`，
全部原样交给它。

托盘图标只有两个状态：**绿色 = 已启用，灰色 = 已暂停**，颜色一眼就能看清，
鼠标悬停有完整文字说明。

支持四种输入法切换快捷键（设置窗口里选）：

- `Ctrl + Space` —— Windows 默认（默认值）
- `Win + Space` —— Win10/11 输入法循环
- `Shift + Space` —— 部分第三方输入法
- `Ctrl + Shift + Space` —— 传统中文输入法

另外还有一个全局热键 `Ctrl + Alt + C`，和 `Ctrl+Caps` 等效 ——
给不习惯拿 Caps 当修饰键的人留的后路。

## 三、为什么单独做了一个「暂停」键

这是我觉得比同类工具想得更远的一点。

写代码、打游戏、或者临时要把 Caps Lock **真的当大写锁定用**的时候，你会希望它能被关掉。
但退一步想：**如果一个工具被暂停之后就再也叫不醒了，那这个暂停功能就是残废的。**

所以有了 `Ctrl + Caps`。它的实现上有个不太显然的约束：

> 键盘钩子必须从启动起**全程常驻**，暂停时也不卸载。
> 因为识别 `Ctrl+Caps` 本身就依赖这个钩子，而它的职责之一正是把程序从暂停态拉回来 ——
> 一旦暂停就把钩子摘掉，就再也没有任何键盘通路能唤醒它了。

于是「启用 / 暂停」在代码里只是**一个标志位**，钩子始终挂着，回调每次读它决定
「重映射」还是「原样透传」。语义上「暂停 = 系统原生行为」没有半点打折。

顺带一个考虑：`Ctrl + Caps` 这个组合在原始需求里本来就是「只吞掉、不做任何动作」的空操作，
拿来复用正好，不占用任何有用的快捷键。

## 四、一些工程上的取舍（可能比功能本身更有意思）

### 1. 为什么切换键是 Ctrl+Caps，而不是 Win+Caps

我一开始选的是 `Win + Caps`，很快就撞墙了：

Caps 被钩子吞掉之后，系统认为 Win 是「**按下又抬起的孤儿键**」，于是啪地弹出开始菜单并抢走焦点。
系统的判据是「Win 按下与抬起之间有没有别的按键事件」—— 而我们要吞的**恰恰就是那个事件**。

补救办法是再补发一个占位按键（AutoHotkey 的 `#MenuMaskKey` 就是这么做的，早期用 `vk07`，
该键码后来被 Xbox Game Bar 占用，文档已改用 `vkE8` 或 `vkFF`）。

**这是依赖未文档化行为的补救** —— 微软随时可以把某个「空闲」键码正式指派功能，
而 `Control` 完全没有这个问题：单独按 Ctrl 什么也不做，吞掉 Caps 之后系统什么都看不到，不会弹菜单。

> 所以：不用 `Win+Caps` 不是「懒得做」，是不想埋一个随时会响的雷。

### 2. 钩子回调里绝不干重活

低级键盘钩子（`WH_KEYBOARD_LL`）的回调跑在**系统输入处理路径**上，
它慢一点点，整台机器的键盘输入都会跟着卡。而「切换启用/暂停」这件事要做托盘刷新、要写配置文件。

所以回调里只做一件事：`PostMessage(CAPS_WM_TOGGLE)`，把活丢给宿主窗口的消息循环。

### 3. 两条防回环防线，一条都不能少

程序自己会 `SendInput` 注入 `Ctrl+Space`。这条注入的按键同样会走一遍钩子 —— 不处理就是死循环。

- **第一道**：注入的按键带自定义签名（写进 `dwExtraInfo`），见到就放行；
- **第二道**：**任何**带 `LLKHF_INJECTED` 标志的事件一律放行 ——
  保证程序只对**物理键盘**动作做决策，别的软件注入的按键它一概不碰。

### 4. 零运行时依赖，并且用 CI 守住它

静态 CRT（`/MT`）编译，**不需要装任何运行库**，拷过去就能跑。
但「零依赖」这种事靠人工自觉是不行的 —— 某天随手改一个编译开关就破功了。

所以 CI 里有一条断言：**扫 PE 导入表里的 DLL 名，出现 `VCRUNTIME` / `MSVCP` / `ucrtbase` /
`MSVCPI` / `api-ms-win-crt` 就判定失败**。

```
== bin\CapsSwitch-x64.exe ==
   导入: ADVAPI32.DLL, COMCTL32.DLL, GDI32.DLL, KERNEL32.DLL, SHELL32.DLL, USER32.DLL
零运行时依赖校验通过。
```

### 5. `--selftest`：一个给脚本用的退出码契约

无人值守环境需要一个可靠的「这程序到底能不能跑」判据。

正常模式下初始化失败会弹一个 **阻塞的** MessageBox —— 脚本只能看到「进程还活着」，
**反而会把失败判成通过**。这个坑我在 CI 里踩过一次，于是加了 `--selftest`：

```
CapsSwitch-x64.exe --selftest & echo %ERRORLEVEL%
```

照常走完整个初始化链路（消息宿主窗口 → 托盘图标 → 键盘钩子 → 全局热键），
然后立即退出，**全程不弹任何对话框**、不进消息循环，用退出码报告结果：

| 退出码 | 含义 |
|---|---|
| 0 | 初始化全部成功 |
| 1 | 单实例互斥体创建失败 |
| 2 | 已有实例在运行 |
| 3 | 消息宿主窗口类注册失败 |
| 4 | 消息宿主窗口创建失败 |
| 5 | 托盘图标挂载失败 |
| 6 | 键盘钩子安装失败 |

因为钩子全程常驻，**自检一定会验到钩子这一环 —— 配置里写着「暂停」也照样验**。
否则某些机器上「钩子被安全软件拦掉」这类故障会被整片漏掉。

## 五、透明与安全

这类工具最容易被怀疑「你是不是在偷键盘」。所以把边界说清楚：

- **不需要管理员权限**，全程不弹 UAC；
- **不写系统目录、不装服务、不联网**；
- 注册表只碰一处：`HKCU\...\Run` 下的开机启动项，且只在你自己勾选时写；
- 配置只写 `%APPDATA%\CapsSwitch\config.ini`，启动时**只读不写**，
  只有你改动过设置才落盘；
- **绿色免安装**，删掉 exe 就干净了（要连配置一起删，删掉 `%APPDATA%\CapsSwitch` 目录）；
- 全部源码开源，逻辑集中在 `hook.cpp` 一个文件里，**就是为了方便单独审查**。

### 已知限制（如实说）

- **UAC 提权窗口、部分以管理员权限运行的全屏程序收不到键盘事件。**
  这是 Windows 的 UIPI 机制限制，不是 bug。需要覆盖的话得改成 `requireAdministrator`
  重新编译，代价是每次启动弹 UAC、且不能再用 HKCU 静默自启。
- 如果 `Ctrl+Space` 已经被其他软件占用（某些输入法会自己拦截），
  本程序不做规避，请在设置里换一种模式。
- 托盘图标在 **16×16 那一档**，「Caps」五个字母会被压缩成一条模糊的横向亮带 ——
  这是像素数决定的，任何 5 字母字标在 16px 下都一样。状态区分主要靠颜色（绿/灰），
  tooltip 里也有完整文字。
- 用 MSVC 14.51（VS 2026 工具集）编译，代码只用了 Win7 就有的 API，
  但微软自 VS2022 17.10 起已把 Windows 7 移出官方支持矩阵，**Win7 上属于「未官方支持」状态**。
  Win7 是硬性目标的话，建议用 v142/v141 工具集重编一遍。

## 七、技术栈与代码结构

**纯 Win32 API，C++17，不用 MFC / Qt / .NET / 任何第三方库。** 约 1900 行。

| 文件 | 职责 |
|---|---|
| `src/hook.cpp` | `WH_KEYBOARD_LL` 键盘钩子与按键注入 —— **核心逻辑全在这里** |
| `src/main.cpp` | 进程入口、消息循环、状态中枢 |
| `src/tray.cpp` | 托盘图标、tooltip、右键菜单 |
| `src/settings.cpp` | 设置窗口（`CreateWindowEx` 手工搭控件，无资源模板） |
| `src/config.cpp` | `config.ini` 读写、开机启动注册表项 |
| `src/crt_free.cpp` | 无 CRT 构建专用的进程入口与内存函数（默认构建不含） |

设置窗口是手工 `CreateWindowEx` 搭的，配合 `IsDialogMessage` 补上 Tab 遍历、
回车触发默认按钮、Esc 关闭这些「对话框行为」，比资源模板更可控。

构建方式：

```bat
build.bat              :: 构建 x64 + x86（默认）
build.bat nocrt        :: 无 CRT 精简版

:: Git Bash / MSYS2 下也可以（不依赖注册表定位 SDK）
bash tools/build_local.sh
```

托盘图标也是生成的：`tools/make_icons.py` 读两张 PNG 设计稿，裁掉透明留白后
按面积平均降采样，打包成含 16×16 / 32×32 两档的 ICO —— **纯标准库实现，不含 Pillow 等第三方依赖**。

## 八. 自己踩过的两个 build.bat 坑（给写 CI 的人）

这两个问题**只在 CI 上才暴露**，本地一直好好的，挺典型：

1. **换行符**。`build.bat` 原先以 LF 入库。`cmd.exe` 解析批处理是**按字节偏移找标签**的，
   LF-only 的文件会让 `goto` / `call :label` 跳到错误位置，症状是「找不到批次标签」。
   已改成 CRLF，并在 `.gitattributes` 里用 `*.bat text eol=crlf` 钉死。

2. **环境残留**。同一个 cmd 进程里连续调两次 `vcvarsall`（先 x64 再 x86），
   而 `vcvarsall` **默认并不会重置** `INCLUDE` / `LIB`。它内部转调的
   `vsdevcmd\ext\vcvars.bat` 写的是**前置追加**：

   ```bat
   set "LIB=%__VCVARS_ADD_TO_LIB%;%LIB%"
   ```

   于是第二轮编译会带着上一轮 x64 的 LIB 路径，链接期报 `LNK1112`「模块计算机类型冲突」。
   现在每次切架构前先把 `PATH/INCLUDE/LIB/LIBPATH` 整体还原到快照。
