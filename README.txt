CapsSwitch 1.0 — 使用说明
===============================================================================

一、这是什么
-------------------------------------------------------------------------------
把键盘上位置很好、但使用频率极低的 Caps Lock 键，重映射成「切换输入法」。

  * 单独按 Caps Lock  -> 发送你配置的输入法切换快捷键（默认 Ctrl + Space）
  * Shift + Caps Lock -> 放行给系统，执行原生大写锁定（两种 Shift 都行）
  * Ctrl + Caps Lock  -> 切换「启用 / 暂停」，启用、暂停两种状态下都有效
  * 暂停状态下        -> 除 Ctrl+Caps 外完全不干预，Caps Lock 恢复系统原生行为

程序没有主窗口，常驻托盘，只靠一个托盘图标交互。适合从 Mac 转过来、
习惯了「按 Caps 切中英文」的用户。


二、安装与运行
-------------------------------------------------------------------------------
1) 选中与你的系统位数一致的 exe：
     * 64 位系统（Win10/11、Server 2022/2025）  -> CapsSwitch-x64.exe
     * 32 位系统（部分 Win7）                   -> CapsSwitch-x86.exe
2) 直接双击运行。首次运行会常驻托盘，不会弹出任何窗口。
3) 不需要管理员权限。不需要安装，删除文件即卸载干净
   （如需同时清理配置，删掉 %APPDATA%\CapsSwitch 目录即可）。

本程序不写系统目录、不装服务、不改注册表里除「开机启动」项以外的任何内容。


三、操作方式
-------------------------------------------------------------------------------
托盘图标左键单击    切换「启用 / 暂停」

托盘图标右键菜单
    启用（Caps→输入法）  Ctrl+Caps    单选，与「暂停」互斥
    暂停（原生 Caps）    Ctrl+Caps    单选
    ----------------------
    开机启动                          勾选项
    设置...                           打开设置窗口
    ----------------------
    退出                              卸载键盘钩子、移除托盘图标、退出进程

全局热键
    Ctrl + Caps Lock   切换「启用 / 暂停」
    Ctrl + Alt + C     切换「启用 / 暂停」（等价，供不习惯 Caps 组合时使用）

    两个都是「切换」，不是单向开关。Ctrl+Caps 走的是键盘钩子，因此**在暂停
    状态下依然有效** —— 这是把程序重新打开的唯一键盘通路，别把它和
    「单独按 Caps 切换输入法」搞混（后者只在启用状态下生效）。

图标状态
    启用    绿色图标，tooltip 显示「已启用（Caps→输入法，Shift+Caps→大写）」
    暂停    灰色图标，tooltip 显示「已暂停（原生 Caps Lock）」

命令行自检
    CapsSwitch-x64.exe --selftest & echo %ERRORLEVEL%

    带上这个参数启动时，程序照常走完整个初始化流程（消息宿主窗口 ->
    托盘图标 -> 键盘钩子 -> 全局热键），然后立即退出并用退出码报告结果，
    全程不弹任何对话框。其中**键盘钩子这一环不受配置里的启用状态影响、
    必定被执行到**（钩子全程常驻，见第九节第 7 条），所以哪怕配置文件里
    写的是暂停，自检也会如实报告钩子能不能装上。退出码含义：

        0    初始化全部成功
        1    单实例互斥体创建失败
        2    已有实例在运行
        3    消息宿主窗口类注册失败
        4    消息宿主窗口创建失败
        5    托盘图标挂载失败（Shell_NotifyIcon）
        6    键盘钩子安装失败（SetWindowsHookEx）

    适合放在安装脚本里做环境预检，或者排查「为什么这台机器上没生效」。
    CI 的冒烟测试用的就是它（原因见第六节）。


四、配置文件
-------------------------------------------------------------------------------
路径：%APPDATA%\CapsSwitch\config.ini
（例如 C:\Users\你的用户名\AppData\Roaming\CapsSwitch\config.ini）

[General]
Enabled=1        ; 0/1  是否启用 Caps 替换
AutoStart=0      ; 0/1  是否开机启动（仅作记录，实际以注册表为准）
HotkeyMode=0     ; 0-3  切换输入法的快捷键模式

HotkeyMode 取值：
    0 = Ctrl + Space          Windows 默认输入法切换（默认值）
    1 = Win + Space           Win10/11 输入法循环
    2 = Shift + Space         部分第三方输入法
    3 = Ctrl + Shift + Space  传统中文输入法

写入时机（严格按规格）：
    启动时只读取、不写盘；只有在托盘菜单切换、或设置窗口里改动过，
    才会把配置落盘。所以全新安装时该文件可能还不存在，属正常。
    仓库根目录的 CapsSwitch.ini 是一份带注释的示例，可直接复制改名使用。


五、开机启动
-------------------------------------------------------------------------------
实现方式：在 HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run
写入名为 CapsSwitch 的字符串值，内容为当前 exe 的完整路径（带引号）。

  * 只写 HKCU，因此不需要管理员权限，也不会弹 UAC；
  * 勾选时写入，取消勾选时删除该值；
  * 启动时读注册表判断当前状态（托盘菜单的勾选状态以此为准）；
  * 如果 exe 被移动到别的目录，下次启动会自动把注册表里的旧路径更新为新路径。


六、构建
-------------------------------------------------------------------------------
依赖：Visual Studio 2019/2022/2026，安装时勾选「使用 C++ 的桌面开发」
     （含 MSVC 工具集与 Windows SDK）。

Windows 命令行：
    build.bat              构建 x64 + x86（默认）
    build.bat nocrt        构建无 CRT 精简版

Git Bash / MSYS2（不依赖注册表定位 SDK，实测验证过的路径）：
    bash tools/build_local.sh
    bash tools/build_local.sh nocrt

产物在 bin\ 目录。

重新生成托盘图标（可选，需要 Python 3，无第三方依赖）：
    python tools/make_icons.py
    脚本会读取 icons\source_on.png（绿）与 icons\source_off.png（灰）
    两张设计稿，裁掉透明留白后按面积平均降采样，再打包成含
    16x16 / 32x32 两档的 ICO。换图标时直接替换这两张 PNG 重跑即可。

持续集成（GitHub Actions）
    .github\workflows\build.yml 在每次 push / PR 时自动构建，产物可在
    Actions 页面下载（artifact 名 CapsSwitch-windows，保留 30 天）。
    打 v* 标签（例如 git tag v1.0 && git push origin v1.0）会额外创建一个
    Release，并附上打包好的 CapsSwitch-<标签名>.zip。

    流水线里除了构建，还跑两条有实际意义的断言：
      * 零运行时依赖校验 —— 扫 PE 导入表里的 DLL 名，一旦出现
        VCRUNTIME / MSVCP / ucrtbase 之类就判定失败。规格里「零运行时
        依赖」是一条硬指标，这里用 CI 守住它，而不是靠人工自觉。
      * 冒烟测试 —— 用程序自带的 --selftest 开关（见第三节的「命令行
        自检」）跑一遍初始化，退出码不为 0 即失败。

    这里刻意没有采用「启动 exe 等 3 秒、看进程是否还活着」这种常见写法：
    托盘挂载失败时程序会弹一个**阻塞的** MessageBox，进程会一直挂在那儿，
    「还活着」的断言反而会把失败判成通过。用 --selftest 才能拿到确定的
    结论，而且失败时能直接看出是卡在哪一环。

    如果哪天 runner 会话确实没有桌面外壳（explorer.exe 未运行），
    自检会返回 5 并在日志里给出提示 —— 那属于环境限制，不是代码缺陷。

    本地自检（改了 workflow 后建议跑一次）：
        python tools\lint_workflow.py
        它把 yml 里每个步骤的 run 脚本抽成独立文件放到 obj\lint\，
        方便逐个过语法检查，同时核对 ${{ }} 表达式是否配对。


七、兼容性与已知限制
-------------------------------------------------------------------------------
支持的平台
    Windows 7 Sp1 及以上、Windows 10/11、Server 2012 及以上、
    Server 2022 / 2025。x64 与 x86 两个版本各自独立。

关于 Windows 7 的注意事项
    本工程用 MSVC 14.51（VS 2026 工具集）编译。微软自 VS2022 17.10 起
    已把 Windows 7 移出官方支持矩阵，代码本身只用了 Win7 就有的 API，
    但在 Win7 上属于「未官方支持」状态。如果 Win7 是硬性目标平台，
    建议改用 v142/v141 工具集重新编译一遍并实机验收。

已知限制
    * UAC 提权窗口、以及部分以管理员权限运行的全屏程序，在非管理员
      运行时收不到键盘事件。这是 Windows 的 UIPI 机制限制，不是 bug。
      需要在提权窗口里也生效的话，把 src\CapsSwitch.manifest 中的
      requestedExecutionLevel 改成 requireAdministrator 后重新编译。
      代价是每次启动都会弹 UAC，且不能再用 HKCU Run 项静默自启。
    * 如果 Caps Lock 的输入法切换快捷键已被其他软件占用（例如某些
      输入法自带 Ctrl+Space 拦截），本程序不做规避，请自行在设置里
      换一种模式。
    * 系统休眠 / 唤醒后钩子会自动保持，无需重新注册。
    * 托盘图标在 16x16 这一档，「Caps」五个字母会被压缩成一条模糊的
      横向亮带 —— 这是像素数决定的，任何 5 字母字标在 16px 下都一样。
      状态区分主要靠颜色（绿 / 灰），tooltip 里也有完整文字说明。
      如果希望 16px 下也清晰，可以另做一版简化的小尺寸设计稿
      （例如只保留字母 C，或只留键帽 + 状态点），单独替换即可。

九、实现说明（相对规格书的几处落地取舍）
-------------------------------------------------------------------------------
1) 设置窗口的「确定 / 取消」语义

   规格里同时写了「复选框实时生效」「下拉框选择后即时保存」和
   「取消放弃未保存修改」，字面上互相冲突。落地取舍是：

       任一控件变化 -> 立即生效并落盘      （满足前两条）
       打开窗口时对配置拍一张快照
       「取消」 -> 把快照写回去            （满足第三条，放弃本次改动）
       「确定」 -> 直接关闭，不做额外回滚

   如果期望的是标准对话框语义（改动只在点「确定」后才生效），
   把 settings.cpp 的 OnCommand 改成「只改局部变量、确定时统一提交」即可。

2) 位数选择

   规格只写了「Windows 7 / 10 / 11 / Server 2022 / 2025」，没有指定位数。
   考虑到大量 Win7 装机是 32 位，这里同时产出 x64 与 x86 两个版本。

3) 体积

   规格写的「< 100KB」经确认不是硬性要求。默认构建用静态 CRT（/MT），
   零运行时依赖，x64 约 121KB、x86 约 105KB，可读性与可维护性优先。
   如果哪天真的需要极致体积，build.bat nocrt 会走一条完全不带 C 运行库
   的构建路径（自备进程入口），x64 约 27KB，代价是失去 /GS 栈保护。

4) 开机启动的事实来源

   config.ini 里保留 AutoStart 字段（规格要求），但程序判断「当前是否
   开机启动」一律以注册表 Run 项为准，避免两边不一致。写失败时不会
   只改内存状态，菜单勾选与实际行为永远同步。

5) 规格未提但补上的三点

   * Explorer 崩溃重启后会广播 TaskbarCreated，不重新挂载的话托盘图标
     会永久消失。tray.cpp 已处理。
   * 按住 Caps 不放时系统会产生自动重复的 KEYDOWN，这里只在首次按下
     发送快捷键，避免连发一串切换。
   * --selftest 命令行自检（退出码见 app.h 的 CapsSelfTestExit）。
     起因是无人值守环境需要一个可靠的「这程序到底能不能跑」判据：正常
     模式下初始化失败会弹阻塞的 MessageBox，脚本只能看到「进程还在」，
     会把失败当成功。自检模式把整条初始化链路的结果收敛成一个退出码，
     且全程不弹窗、不进消息循环。

6) 启用 / 暂停的切换键选了 Ctrl + Caps，而不是 Win + Caps

   两个组合都能做，但 Win + Caps 有个绕不开的坑：Caps 被钩子吞掉之后，
   系统认为 Win 是「单独按下又抬起」的孤儿键，于是弹出开始菜单并抢走焦点。
   系统判断「是不是孤儿」的依据是 Win 按下与抬起之间有没有别的按键事件 ——
   而我们要吞的恰恰就是那个事件。补救办法是再补发一个占位按键：AutoHotkey
   的 #MenuMaskKey 就是这么做的，早期用 vk07，该键码后来被 Xbox Game Bar
   占用，文档已改用 vkE8（微软标注为 unassigned）或 vkFF（no mapping）。
   这属于依赖未文档化行为的补救 —— 微软随时可以给某个「空闲」键码指派
   功能，而 Ctrl 完全没有这个问题：单独按下 Ctrl 什么也不做，吞掉 Caps 后
   系统什么都看不到，也不会弹菜单。

   相应地，Ctrl + Caps 顶替了规格 2.1 中「Ctrl / Alt + Caps 只吞掉、不切换
   输入法」里 Ctrl 的那一半 —— 那个组合本来就是空操作，正好拿来当切换键。
   Alt / Win + Caps 保持原样：只吞掉 Caps，不做任何动作。

7) 键盘钩子改为全程常驻（暂停时不卸载）

   起因是 Ctrl+Caps 的职责之一就是把程序从暂停状态重新打开，而它本身也要
   靠这个钩子来识别。原先「暂停就 Hook_Uninstall」的写法会陷入死结：钩子
   一卸，就再没有任何键盘通路能唤醒程序了。现在钩子自启动起一直挂着，
   「启用 / 暂停」只是 g_app.enabled 一个标志位，回调每次读它决定「重映射」
   还是「原样透传」—— 暂停时钩子虽然还挂着，但不做任何干预，
   「暂停 = 系统原生行为」这条语义没有变。

   顺带带来一个收益：自检模式下的钩子检查不再受配置影响，必定执行。否则
   配置写成暂停的机器上，--selftest 会整片漏掉「钩子被安全软件拦掉」这类
   故障。

   另一处细节：切换动作不在钩子回调里直接执行。回调跑在系统输入处理路径
   上，必须尽快返回，而一次切换要刷新托盘、写配置文件。所以回调只投递一条
   CAPS_WM_TOGGLE 消息，真正的工作交给宿主窗口的消息循环。

8) 上 CI 时修掉的两个 build.bat 隐患

   * 换行符：build.bat 原先以 LF 入库。cmd.exe 解析批处理是按字节偏移
     找标签的，LF-only 的文件会让 goto / call :label 跳到错误位置，症状
     是「找不到批次标签」或在错误的行继续往下执行。已改为 CRLF，并在
     .gitattributes 里用 *.bat text eol=crlf 钉死，防止再次被检出成 LF。
   * 环境残留：build.bat 在同一个 cmd 进程里连续调用两次 vcvarsall
     （先 x64 再 x86），而 vcvarsall 默认并**不会**重置 INCLUDE / LIB。
     它内部转调的 vsdevcmd\ext\vcvars.bat 写的是前置追加：
         set "LIB=%__VCVARS_ADD_TO_LIB%;%LIB%"
     vsdevcmd.bat 对 INCLUDE 同样是前置追加。只有显式传 /clean_env 才会
     清空，而那条路径会直接跳过架构初始化。所以第二轮编译会带着 x64 的
     LIB 路径，链接期可能报 LNK1112「模块计算机类型冲突」。
     现在在第一次调用前把 PATH / INCLUDE / LIB / LIBPATH 整体快照，
     每次切架构前先还原再 call。
     （tools\build_local.sh 没这个问题——它每个架构都自己重新拼 INCLUDE
     和 LIB，所以本机一直没暴露出来。）
